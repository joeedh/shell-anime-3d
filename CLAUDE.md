# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a test app for the shell-outline concept in `docs/shell-outline.md`. The implementation
plan, with the status of each milestone, is `docs/plans/test-app.md`. How the clip models
work now is in `docs/clip-models.md`.

Stack:

- **Language:** TypeScript.
- **Runtime:** NW.js running WebGPU.
- **UI:** path.ux, consumed as TypeScript source from the `extern/path.ux` submodule through
  `src/pathux.ts`.
- **Serialization:** nstructjs, from the `extern/nstructjs` submodule.
- **Package manager:** pnpm.
- **Linting:** lintrix. The source checkout at `C:\dev\fastlint` documents the config and
  rules.
- **Formatting:** `@pathtx/prettier`.

## Commands

```bash
pnpm install                 # after cloning: also run git submodule update --init --recursive
pnpm run build               # esbuild: src/main.ts -> app/dist/app.js
pnpm run start               # build, then launch NW.js with CDP on port 9222
pnpm run cdp logs 5          # reload the running app and print console output for 5 s
pnpm run cdp eval "<expr>"   # evaluate JS in the running app (awaits promises)
node tools/cdp.mjs eval "$(cat script.js)"   # multi-line scripts (pnpm mangles the quoting)
pnpm run cdp screenshot f.png
pnpm run start -- --renderdoc    # launch under RenderDoc; then `pnpm run rd capture|actions|pick|debug`
pnpm run typecheck           # tsgo --noEmit
pnpm run test                # vitest
pnpm run lint                # lintrix src tests
pnpm run format              # prettier --write
```

## Things that bite

- **GPU debugging:** see "GPU debugging toolkit" in `docs/debugging.md` (compare pass,
  RenderDoc pixel debugging with WGSL names, nsys timing). `tools/nw.mjs` forces the
  discrete GPU; Chromium otherwise picks the integrated one on hybrid laptops.
- **There is only one nstructjs.** Both `tools/build.mjs` and `vitest.config.ts` alias every
  `"nstructjs"` import, path.ux's included, to `extern/nstructjs/build/nstructjs_es6.js`.
  - Never run `pnpm install` inside `extern/path.ux`; it would create a second struct
    registry.
  - Prefix struct names with `sa3d.`.
- **Modules that register things need side-effect imports.** A module that registers an area,
  element or struct must be imported for its side effects. esbuild drops imports used only as
  types (see `docs/debugging.md`).
- **Node modules at runtime:** reach them through `src/core/platform.ts` (`globalThis.require`).
  `import fs from "fs"` fails in NW.js.
- **Scripting the app:** `toolstack.undo()`/`redo()` are async. Tool inputs are
  space-separated in the path (`mesh.smooth(factor=0.3 iterations=2)`), and path.ux
  remembers the last values used. More in `docs/debugging.md` ("Scripting the app over
  CDP").
- **Undo:** `src/core/undo.ts` patches `ToolOp.prototype` with whole-scene snapshot undo. Ops
  that change large data override `undoPre`/`undo`/`calcUndoMem`.

## Default rules

### Code comments

- Ordinary code comments (not doc comments) are at most 5 lines.
  - Exception: about one longer comment per 200 lines of code is allowed, for things like a
    section overview or an explanation of a tricky algorithm.
- Doc comments (docstrings, JSDoc, Doxygen, `///`, and the like) have no length limit.
- Math-heavy comments (derivations, formulas, numerical reasoning) have no length limit.
- Temporary comments have no length limit, but must start with `CLAUDENOTE:` so they can be
  found and stripped later (`grep -rn "CLAUDENOTE:"`).

### Documentation and plans

- Documentation goes in `docs/`.
- Plans go in `docs/plans/` and must be committed to the repo, not left in a scratch folder
  or only in the conversation.
- Pressure-test every plan before implementing it, which means trying to falsify it. Always
  do this in a fresh subagent: give it the plan and the code, but not your reasoning, so its
  attempt is not anchored on the author's view. Tell it to:
  - List the claims the plan depends on (about the code, the data, performance, APIs) and
    try to prove each one false: read the code, run a quick experiment, or find a
    counterexample.
  - Construct concrete inputs or scenarios that would make the plan fail.
- Record in the plan file which claims survived, which broke, and how the plan changed.
- Keep a running debugging guide in `docs/debugging.md`. When a bug takes real effort to
  track down, add an entry: symptom, cause, fix, and how to spot it next time.

### File size

- When a source file grows past 35 KB, split it into smaller files.
- Split along real boundaries of responsibility, and give the pieces a subdirectory structure
  that reflects them (for example `parser/lexer.ts`, `parser/ast.ts`), not `foo1.ts` and
  `foo2.ts`.
- Generated files, vendored code, lockfiles, and data files are exempt.
